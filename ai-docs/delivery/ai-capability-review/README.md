## 一、一句话结论

Meetwise 的 AI 底座在**安全和计费上做得很“硬”**：幂等账本、逻辑节点只派发一次、共享熔断、成本预留、RLS checkpoint、数据围栏，都是成熟 agent 产品少见的严谨程度。问题出在它把“绝不重复花钱”做成了“**任何一次失败都是永久失败**”：

- 准入被拒、JSON 格式错、worker 崩溃、DB 抖动、跨场撞题，这些本可恢复的瞬时问题，都会被固定幂等键和 failed/unknown 终态重放“钉死”，最终表现为**面试提前结束、卡住或报告永远出不来**。
- 在体验上，出题模型看不到上一轮作答和简历（#44/#196），“自适应追问”和“个性化”都打了折扣。
- 缓存和成本工程目前基本是“结构上准备好、实际没有收益”。

## 四、与成熟 agent 的对比（只列有把握的公开事实）

| 维度 | Meetwise 现状（本次读码） | Claude Code（Anthropic 公开文档） | 其他成熟方案（公开文档） |
|---|---|---|---|
| 主循环 | 固定拓扑的 LangGraph 状态机（plan→decide→gen→await→eval），模型不选工具，检索由代码前置执行 | 模型驱动的 agentic 循环：模型自行决定调用 Read/Edit/Bash/Grep 等工具，多步迭代直到完成，工具调用受权限模式约束 | LangGraph 本身支持节点级 `retryPolicy`，以及 `durability`（exit/async/sync）模式 |
| 失败恢复 | 不重试；failed/unknown 终态重放；节点不配 retryPolicy（AG-01–06） | 对话中工具失败会把错误回给模型，由模型改道（这是 agentic 循环的基本形态） | LangGraph 的 retryPolicy 可按异常类型、退避参数重试单个节点；Temporal 一类持久执行框架的核心就是对 activity 自动重试 |
| 上下文管理 | 每次调用都是单轮 system + user；超预算直接拒绝；组件裁剪器存在但未接线（AG-20） | 接近上下文上限时自动 compact（摘要压缩历史），也可以手动 `/compact` | — |
| 记忆 | episode 判重 + 弱项名精确匹配，实际恒空（#203/#252）；MEM-* 原语未接线 | `CLAUDE.md`（项目级/用户级）作为持久指令记忆，会话开始时自动加载，可用 `/memory` 编辑 | Letta（MemGPT）：核心记忆块常驻上下文，档案/回忆记忆走检索，由 agent 通过工具自主编辑记忆 |
| 子任务隔离 | 无 | 支持 subagent，每个有独立上下文窗口 | — |
| 工具与扩展 | 请求体没有 tools；runToolLoop 只导出未使用（AG-38） | 内置工具 + MCP 服务器扩展 + hooks（工具调用前后执行用户脚本） | OpenAI / Anthropic API 都原生支持 function/tool calling |
| Prompt 缓存 | 前缀稳定但全部 <1024 token（实测 172–670），百炼下无法命中；不读 cached_tokens（#48/#49） | 默认启用 Anthropic prompt caching（提供 `DISABLE_PROMPT_CACHING` 环境变量关闭） | Anthropic：`cache_control` 断点，最小可缓存 1024 token（主力模型），命中按基础输入价 10% 计；OpenAI：≥1024 token 的提示自动缓存，`usage.prompt_tokens_details.cached_tokens` 回报命中量；百炼：显式/隐式均 ≥1024 token，隐式命中按 20% 计价；DeepSeek：默认开启硬盘缓存，`prompt_cache_hit_tokens` 回报命中量 |
| 结构化输出 | `json_object` + 本地 zod 校验，失败不重试（AG-17） | — | OpenAI Structured Outputs：`json_schema` + `strict: true` 让输出受 schema 约束 |
| 计费与幂等 | 账本级幂等、逻辑节点只派发一次、共享熔断与成本预留，**严格程度高于常见 agent** | 面向开发者的按量计费，没有业务级幂等账本这一层 | — |

> 对比只说明“业界通行做法”，不意味着 Meetwise 必须照搬。面试场景要求可审计、可计费、受控出题，固定拓扑本身是合理选择。真正要补的是**失败语义**（可重试 vs 终态）和**上下文供给**（作答/简历/已问题目进 prompt）。

## 五、修复优先顺序建议

1. **先修失败语义**（AG-01/02/03/04/05/06 一起做）：准入拒绝属于“没发出去”，要释放 claim；HTTP 200 但 JSON 坏了按“已执行的确定性失败”结算；出题和报告的重试同时换 idempotencyKey 和 businessRevision（形如 `…:a${n}`）并设上限；alreadyApplied 时用 `invoke(null)` 续跑；consumer 区分瞬时错误和确定性错误。配上 AG-15 的卡死检测和 AG-16 的确定性 proof。
2. 把作答摘要、近 N 题避重清单、简历事实（在已同意用途内）放进出题 prompt（#44/#196、AG-02）。
3. 成本侧：关停或改造校准对账（AG-07）；预留改用估算值（AG-11）；熔断键按端点区分（AG-08）；接 cached_tokens 观测后再决定要不要做显式缓存（#48）。

## 设计决策：B 端与 C 端的记忆使用边界（2026-10-12，设计建议，非代码现状）

> 本节是产品/架构设计建议，**不是**当前代码已落地的行为。用于约束后续记忆读写改造，避免把 C 端成长记忆误用于 B 端评估，或把评估结果不当回流。

### 判断原则

记忆用途只有一条分界线：

- **帮用户本人成长** → C 端可用（练习、规划、复盘）。
- **影响他人对其评判** → B 端评估不可用（出题、评分、录用决策不得依赖跨场长期记忆）。

### 规则表

| 场景 | 记忆范围 | 读写 |
|---|---|---|
| C 端练习面试 | 本人长期记忆 | 可读写 |
| C 端成长规划 | 本人长期记忆 | 可读写 |
| B 端岗位面试出题/流程 | **仅本场会话记忆**；面试结束即封存 | 本场可读可写；结束后只读封存、不可再扩写进长期记忆供评估用 |
| B 端评分 | **不读任何跨场记忆** | 只吃本场数据 |
| B 端结果 → C 端 | 默认**不回流**；候选人明确同意后，仅回流本人可见的弱项摘要 | 需同意记录 |
| C 端练习 → B 端 | **永不流向** B 端 | 硬禁止 |

### 两条底线

1. **本场会话记忆**：B 端与 C 端都可用（支持追问、上下文连贯）。
2. **跨场长期记忆**：只在 C 端、且仅本人可见；B 端评估链路不得读取。

### 实现建议

1. **用途标签**：记忆读写一律带用途标签，至少区分 `c_practice` / `c_growth` / `b_assessment`。
2. **读取拦截**：读取接口按用途过滤；`b_assessment` 对跨场长期记忆**固定返回空**（含弱项投影、episode 判重若会泄露成长画像则同样拦截）。
3. **主体隔离**：C 端记忆归本人；B 端记忆归「企业 + 该场面试」；两端互通必须有同意记录（consent），默否认。
4. **评分节点**：只消费本场会话数据与本场产物，禁止注入历史弱项、跨场 episode、成长档案。

### 现状（代码未区分两端）

当前实现**未按 B/C 端区分记忆用途**，自适应面试出题链路共用同一套历史弱项只读投影（从 `assessment_report` 取 `gap=true` 维度名做软偏置），不区分该场是 C 端练习还是 B 端岗位面试：

- 弱项投影 SQL / 库层：`packages/db/src/memory-store.ts:47`（`historicalWeakDimensions`）
- Worker 封装：`apps/worker/src/memory-service.ts:31`（`pastWeakDimensions`）
- 出题侧调用：`apps/worker/src/adaptive-interview-service.ts:58` / `:66`（`biasByPastWeakness` → `pastWeakDimensions`）

上述路径按 `owner` 读取历史弱项并软偏置能力顺序，**没有** `c_practice` / `b_assessment` 一类用途拦截；若 B 端岗位面试复用同一 worker 路径，则会读到跨场弱项——与本节「B 端评估不可用跨场记忆」的设计建议不一致，属待改造点（设计建议，非本次改码）。
