# 专家级训练库：产品、C/B 招聘与数据评测

## 缩略语阅读卡

`C 端（面向个人候选人的产品）`、`B 端（面向企业招聘方的产品）`。本页其余缩写首次含义统一如下，后文为口述流畅可简称；完整术语表见 [统一术语](/ai-docs/product/glossary.md)。`RAG（检索增强生成；检索受控证据后回答）`、`LLM（大语言模型；生成语言但不直接授权）`、`CAS（比较并交换；并发下只在预期状态更新）`、`RLS（行级安全；数据库逐行隔离权限）`、`SSE（服务器发送事件；服务端到浏览器的流式推送）`、`ASR（自动语音识别；把音频转成文本）`、`PII（个人可识别信息；需要用途限制和脱敏）`、`E2E（端到端测试；验证完整链路）`、`P95/P99（第 95/99 百分位延迟；衡量尾部慢请求）`。

> 这组题不以“知道 RAG / LangGraph / 多 Agent 名词”为得分依据。候选人必须说明领域边界、状态机、数据副作用、失败路径和可验证指标。每题均要求考官追加至少一个指代、事实纠正、重复提交、越权、撤回同意或模型超时场景。

## 使用规则

- 共 15 题，每题 10 分，总分 150 分；初级 40 分、中级 60 分、高级 50 分。
- 每题至少要求候选人给出：一个状态机或数据模型、一个失败路径、一个量化验收指标。
- 不可只问 happy-path。若候选人只给主流程，没有处理非理想输入、并发或权限边界，单题最高 4 分。
- 含有评分、招聘、支付、同意、隐私、题库或模型调用的题目，必须说明 CAS、幂等键、RLS principal 绑定、持久有序事件日志中哪些原语生效。

## 初级（4 题）

### EXP-C1-01：用户纠正简历事实时，Agent 应如何停止沿用错误前提？

**场景**

系统问：“你简历中提到用 PostgreSQL 支撑订单高并发更新，为什么选 `SELECT FOR UPDATE` 而不是乐观锁？”用户回答：“你上面说的那个为什么要这么做？另外 PostgreSQL 那段是 AI 自动补的，我没做过。”设计这一轮的处理逻辑。要求不能给用户打低分，不能继续把“订单高并发更新”作为事实追问。

**考察点**

- 指代消解与事实纠正是两类不同输入。
- 模型生成的简历断言不能覆盖候选人的显式纠正。
- 问题、评分、证据、简历快照之间的可追溯关系。
- “澄清一次”与“无限追问”的边界。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 继续回答 PostgreSQL 问题，或给回答计分。 |
| 4 | 能识别“用户没回答”，但没有保存纠正事实、没有撤销原题前提。 |
| 7 | 将本轮标为 `resume_correction`，原题不计分，下一题改为通用基础题或允许跳过。 |
| 10 | 增加证据快照、纠正事件、问题失效事件、幂等键；给出多轮和重放测试，且定义“重复错误前提=0”的发布门。 |

**标准答案**

**90 秒可口述完整答案**

我会把候选人的“这段是 AI 自动补的，我没做过”当成对证据事实的纠正，而不是一次低质量回答；结论是纠正优先于评分和追问。当前题的前提来自哪一份简历快照、哪一个 `factId`、哪条生成证据，必须可追溯。只要候选人明确否认，该断言立即失去继续自动出题的资格；“你上面那个为什么”则是另一个指代问题，最多围绕当前题澄清一次，不能掩盖前提已被否认这一事实。

处理流程上，输入先绑定当前 `interviewId`、`turn`、`questionId` 和简历快照，再同时产出“纠正事实”和“是否需要澄清指代”两个结构化判断。服务端用稳定幂等键写入独立的事实纠正记录，并把依赖该事实的问题标为失效；同一事务追加纠正、问题失效和下一题就绪事件。原题不创建评分、不更新能力画像、不改变难度，也不确认任何消费。下一题只能从仍有效的证据生成，或改为不依赖简历的基础题、允许跳过。

失败时不能为了保持对话连贯继续假定候选人做过该项目。模型无法确认被纠正的具体 span、重复提交、断线重放或人工编辑简历冲突时，回查已持久化的纠正记录；不确定就停止使用该事实并请候选人确认，而不是静默改写简历原文。B 端人员可以提交待确认的资料修订建议，但不能越过候选人把 C 端事实改成真；候选人纠正和后续新简历版本必须保留审计边界。

验证不看“模型是否礼貌道歉”，而看不变量：显式纠正后重复错误前提数为 `0`、同一纠正重放只生成一份记录、原题评分和消费均为 `0`。用多轮指代、两次点击、worker 崩溃恢复、B 端编辑冲突和简历版本切换做集成测试；还要按纠正后成功换题率、误把纠正判成非作答的比例和 P95 收口延迟监控线上效果。

1. 输入必须同时识别 `ask_clarification` 和 `resume_correction`，不能把整句降格为“答非所问”。
2. `resume_correction` 优先级高于普通评分。原题依赖的断言标记 `disputed`，不得再用于本场或后续自动出题。
3. 本轮不创建 `answer_evaluated`，不改变能力分、难度和消费计量。
4. 追加 `fact_correction_recorded`、`question_invalidated`、`question_ready` 事件；新题只能使用未被纠正的简历证据或通用能力。
5. 简历原文不能被系统静默改写。候选人纠正作为独立事实层保存，后续由用户确认是否创建新简历版本。
6. 同一事实重复纠正采用 `interviewId + factId + sourceVersion` 幂等键。

**示例伪代码**

```ts
type TurnIntent =
  | { kind: 'resume_correction'; disputedFactIds: string[] }
  | { kind: 'clarify'; referent: 'current_question' | 'unknown' }
  | { kind: 'answer' }
  | { kind: 'skip' };

if (intent.kind === 'resume_correction') {
  await tx(async () => {
    await recordFactCorrection({
      idempotencyKey: `${interviewId}:${turn}:correction`,
      resumeVersionId,
      disputedFactIds: intent.disputedFactIds,
    });
    await appendEvent(interviewId, 'question_invalidated', {
      questionId,
      reason: 'candidate_disputed_grounding',
    });
  });
  return issueUngroundedSafeQuestionOrSkip();
}
```

**追问**

- “我记不清是不是做过”与“这段是假的”是否进入同一状态？
- 若 B 端招聘人员编辑过候选人档案，谁有权确认事实更正？
- 一道已评分的问题后来被纠正，应否重算报告？如何避免只重算某一位候选人？

**常见错误**

- 把“不会”直接计为 0 分。
- 仅靠 prompt 说“不要幻觉”，没有 `factId` 和证据快照。
- 继续输出“结合你的真实项目经历回答”，形成错误前提循环。

### EXP-C1-02：所有 RAG 项目都需要意图识别器吗？

**场景**

产品经理提出：为“面试训练、题库问答、订单查询、退款、闲聊”统一增加一个 LLM 意图识别器。用户输入：“上面那个为什么更安全？另外我刚才那次能退吗？”说明哪些场景需要路由，哪些不需要；分类结果能否直接执行退款？

**考察点**

- 单库 RAG、跨域检索、工具调用和事务动作的边界。
- 指代消解依赖会话状态，不等于意图识别。
- 安全路由与业务路由的不同失败模式。
- 分类器结果不具备业务授权。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 回答“所有 RAG 都需要意图识别”。 |
| 4 | 列出若干 intent，但未说明误路由后果和回退。 |
| 7 | 区分单知识库检索、跨域路由、业务工具调用；说明退款仍需服务端校验。 |
| 10 | 给出置信度、澄清、默认路由、权限校验、延迟预算和误路由指标。 |

**标准答案**

**90 秒可口述完整答案**

结论是不能把意图识别器当成所有 RAG 的固定前置。若只有一个知识库、同一权限范围和只读问答，直接做检索、重排、引用和资料不足澄清更少一次模型延迟和误分流面；只有问题会在多个知识域、不同权限边界或不同工具能力之间切换时，路由结果才真正改变系统决策，才值得引入路由。

对象和流程要分开：页面中的明确订单 ID、已确认实体或固定按钮先走确定性业务契约；开放文本才由规则和分类器输出受限的候选 route、置信度与澄清原因。“上面那个”先从当前 principal 可见的最近实体中找候选，候选不唯一就问清楚。即使 route 指向账单域，它最多创建一个客服/账单查询的准备动作；退款服务仍需重新核对用户、订单状态、金额、审批条件和幂等键，route 绝不是授权凭证。

失败语义也要按风险分层。低置信、多意图或模型超时时，普通只读问题可落到默认帮助或澄清，不能无限转圈；涉及退款、扣款、隐私读取等高风险路径时，未知或冲突结果必须拒绝执行。分类器和安全策略的日志只记录最小审计信息，不能把候选人答案或简历原文作为路由调试数据泄露出去。

我会分桶报告 route precision/recall、低置信率、澄清后完成率、P95 延迟和 `misroute_to_privileged_action=0`；测试同一句话在不同会话上下文、不同租户、不同订单归属下的结果。面试官若问“为什么不用一个大模型规划全部路径”，我会说明开放规划扩大 tool 面与不可解释性；把路径枚举为有限 capability，再由服务端授权，才能让错分降级为体验问题而非资金或数据事故。

- 单知识库、单入口、只回答资料：通常只需要检索、重排、引用和 `abstain`，不应为了“架构完整”增加分类模型。
- 多知识库、多业务域：需要路由，用于选择 `tech_knowledge`、`billing_support`、`job_application` 等域。
- 退款、扣款、查看订单不是 RAG 输出；路由只能提出“转账单服务”，最终动作必须校验用户、订单状态、金额、权限、幂等键。
- “上面那个”先利用当前题目或最近可见上下文解析；无可解析指代时澄清，不能随机检索。
- 安全分类器失败应 `fail-closed`；普通任务路由失败可 `fail-open` 到默认帮助或澄清，不能让用户卡死。

**示例契约**

```ts
type Route =
  | { action: 'retrieve'; corpus: 'tech'; confidence: number }
  | { action: 'clarify'; reason: 'missing_referent' | 'ambiguous' }
  | { action: 'handoff'; domain: 'billing'; confidence: number }
  | { action: 'redirect'; reason: 'out_of_scope' };

function execute(route: Route, principal: Principal) {
  if (route.action === 'handoff') {
    return billingService.prepareSupportCase(principal); // 不是退款
  }
}
```

**量化验收**

- `route_accuracy` 按意图桶分别计算，不能只报总体准确率。
- `misroute_to_privileged_action = 0`。
- 低置信样本进入澄清或默认路由的比例单独统计。
- 语音热路径路由额外延迟须有 P95 预算。

**追问**

- 安全分类器和普通路由器是否应使用相同的 fail mode？
- “退款”路由成功后，哪些字段仍需账单服务重算？

**常见错误**

- 用大模型处理所有输入。
- 让 `billing` intent 直接调用退款 API。
- 把“它”“上面那个”错误地当成技术检索 query。

### EXP-C1-03：用户双击提交、超时重发后，怎样保证不重复评分和扣费？

**场景**

候选人点击“提交答案”后网络超时，连续重试 3 次；其中第一次请求已经到达服务端。面试完成时还会触发报告生成和权益确认。

**考察点**

- 客户端重试、服务端重放、worker 重领的区别。
- 幂等键、CAS、事件日志和消费账本必须同事务。
- 评分、扣费、模型外呼不能混为“exactly once”。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 只说“前端禁用按钮”。 |
| 4 | 有幂等键，但冲突后静默忽略，不返回第一次结果。 |
| 7 | 同一 `turn` 仅一条评分、一个事件、一笔消费记录。 |
| 10 | 解释“模型外呼无法凭本地数据库单独实现 exactly-once”，提出 provider 幂等、调用账本和崩溃对账。 |

**标准答案**

**90 秒可口述完整答案**

结论是前端禁用按钮只能改善体验，不能提供幂等保证；同一答案提交要被建模为一个带稳定身份的业务命令。我要保证的是同一个 `turn` 最多生成一条已提交评分、一笔消费确认和一个可重放结果，而不是声称跨数据库和模型供应商已经数学意义上的 exactly-once。

流程上客户端首次提交生成 `clientCommandId`，服务端把 principal、面试、题次和该 ID 组合成幂等作用域。服务端短事务中原子写入幂等记录、校验 `InterviewQA` 的期望状态、追加 `answer_evaluated` 预留事件和消费账本预留；重复请求若 payload 相同则返回第一次的状态或结果，若同一键却换了答案内容则明确冲突。模型调用在事务外执行，调用账本从 `reserved` 到 `in_flight`，携带供应商幂等键；校验后的评分、消费确认和完成事件再以短事务提交。

网络超时、worker lease 过期、进程在模型返回与落库之间崩溃时，重试者先读账本而不是重做调用。已提交就返回原结果；仍在飞行且供应商可查询时对账；无法确认的调用进入受限重试或降级并记录不确定成本。不能在数据库长事务、行锁或 advisory lock 中等待模型网络响应，也不能把不同 `clientCommandId` 的完全相同答案盲目折叠，因为用户可能有意修改后重答，去重边界必须是业务命令而非文本相似度。

验证用 20 路同键并发、写幂等记录后故障、状态 CAS 冲突、模型回调重复和 lease 重领来断言评分事件、消费确认和最终报告各为一。线上监控幂等命中、冲突、悬挂 `in_flight` 年龄、对账成功率、重复副作用和不确定费用；这些分子分母比“HTTP 200 比例”更能证明重试没有造成重复扣费。

- 幂等键按用户、面试、题次、答案命令作用域生成，例如 `principal:interviewId:turn:clientCommandId`。
- `idempotency_record`、`InterviewQA` 状态 CAS、`answer_evaluated` 事件、消费确认必须同事务。
- 请求冲突后返回首次结果，不是返回空成功。
- 评分模型调用前需要 `in_flight` 账本；调用后提交已校验结果。崩溃窗口必须可对账。
- 不可在数据库长事务中持锁等待模型网络响应。

**必要测试**

- 同幂等键并发 20 路：`answer_evaluated=1`、`consumption=1`、评分结果相同。
- 在“写入幂等键”和“更新状态”之间故障：重试后副作用仍为 1。
- worker lease 过期重领：不重复落分、不重复确认权益。

**追问**

- 两个不同 `clientCommandId` 却提交完全相同答案，是否应去重？
- 支付回调与业务权益履约如何使用不同的幂等范围？

**常见错误**

- 把 HTTP 200 当作幂等证明。
- 只给订单加唯一键，不给答题、模型调用和报告任务加键。
- 用全局内存 Map 去重，进程重启后失效。

### EXP-C1-04：怎样让评分可解释，但不泄露题库和评分攻击面？

**场景**

候选人质疑：“为什么这题给我 42 分？我回答的就是实际经历。”招聘方又希望看到判断依据。设计 C 端报告、B 端候选人评估和申诉入口。

**考察点**

- 评分证据与标准解、隐藏 rubric 的分层。
- 证据必须绑定题目版本和简历/答案快照。
- 解释、申诉、重算与审计不可互相覆盖。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 返回模型完整推理过程或完整 rubric。 |
| 4 | 只有“优点/缺点”自然语言。 |
| 7 | 每个评分维度都有可定位证据和改进建议。 |
| 10 | 评分版本、题目版本、证据哈希、申诉与统一重算策略齐全。 |

**标准答案**

**90 秒可口述完整答案**

结论是可解释不等于暴露模型的完整推理过程，也不等于把题库标准解和抗作弊规则发给用户。候选人需要知道“哪一项能力、基于自己哪段回答、还缺什么信息、下一步如何改进”；招聘方只需要与岗位相关、已授权且可复核的证据。任何没有证据的维度应显示为不确定或降级，而不是用流畅文字伪造一个分数。

数据模型上，评分结果绑定 question、rubric、prompt/model、简历和答案的冻结版本。每个分数维度保存最小 `evidence_span`，含快照版本、偏移、内容 hash 和问题/rubric 版本；C 端报告从这些 span 生成解释和练习建议，B 端候选评估从独立的岗位快照生成说明，二者不共享 C 端练习原文。申诉创建一个新的 `assessment_version`，重算在明确的版本和统一规则下发生，旧版本保留为 superseded，不能覆盖掉历史审计。

若 evidence offset 已因简历更新失效、模型输出没有通过 schema/业务校验、候选人撤回了共享授权，页面不能继续展示看似精准的旧解释；应回退为“该维度暂无法验证”并引导申诉/人工复核。招聘方没有因为拿到报告就获得 C 端训练历史的读取权，隐藏 rubric、标准解和内部反作弊阈值也不能经 API 或日志侧漏。

验收包括每个非降级维度至少一个可验证证据、无证据强结论数为 `0`、版本错配展示数为 `0`、申诉后旧分不被覆盖以及跨端原文读取数为 `0`。还要抽样人工复核证据定位正确率、跟踪申诉率和人工推翻率；若这些指标变差，不能仅以报告点击率高就认为解释设计成功。

- 面向候选人：展示评分维度、引用其答案片段、缺失的信息、可执行改进建议；不展示题库标准解和抗作弊规则。
- 面向招聘方：展示岗位能力证据、题目版本、报告版本、人工复核状态；不得读取候选人 C 端练习原文。
- 每个非降级评分维度至少有 1 个 `evidence_span`；无证据时结果应为 `inconclusive` 或降级，不应伪造数值。
- 证据绑定 `snapshot_version`、`offset`、`content_hash`、`question_version`、`rubric_version`、`model/prompt version`。
- 申诉不覆盖旧分：创建新的 `assessment_version`，旧版本保留并标记 superseded。

**追问**

- 如何解释分数而不暴露可刷分的 hidden rubric？
- 简历更新后怎样避免旧评分证据指向新文本？

**常见错误**

- 把“可解释”理解成返回链式思维。
- 简历更新后仍按新文本展示旧评分证据。
- 训练问题被召回后，只为某一位候选人重算。

## 中级（6 题）

### EXP-C2-01：如何把“单一高召回率”拆成能反映真实用户的 RAG 评测？

**场景**

当前通用 57-query 合成对抗集的 RRF 消融在多证据 `strict-all@5` 上为 `28/45=62.2%`；它不是当前题库默认策略。另一个 35-query 当前题库 holdout 上 dense 是 `100.0%/100.0%`、RRF 是 `89.5%/91.4%`，两套都仍是本地同域数据。真实用户会输入：“上面那个为什么更安全？”“我不会这个，换个简单的。”“帮我把刚才那题写成自我介绍。”以及英文、拼写错误、代码片段、多个相关证据、完全域外问题。设计真实数据评测集、标注方式、指标和发布门。

**考察点**

- 检索质量与完整 Agent 行为不能混为一个指标。
- 多相关标签、无答案、指代上下文、域外输入。
- corpus version 和 query context 的冻结。
- `top-k` 召回、排序质量、拒答质量的组合。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 增加更多关键词 query 后重跑 recall。 |
| 4 | 有正例和负例，但不含多相关、上下文和拒答。 |
| 7 | 按 query 类别分层，报告 Recall@K、nDCG、abstain。 |
| 10 | 有人工双标、冲突仲裁、版本冻结、置信区间、真实模型端到端回归。 |

**标准答案**

**90 秒可口述完整答案**

我的结论是先把“检索找到了什么”和“Agent 最终做了什么”拆开评测，不能用一个总体 Recall 掩盖多证据遗漏、指代错误或该拒答却外查的问题。题干里的 57-query RRF 消融与 35-query qbank holdout 是不同夹具、不同策略比较；它们只能帮助定位，不是生产质量或统一默认策略的证明。真正发布时必须冻结语料版本、chunk 策略、embedding、reranker、路由策略和会话上下文，才能让一次回归可复现。

数据集以 query、可见上下文、所需证据集合、应答动作和切片标签为最小对象。一道涉及状态机和幂等的题可有多个 required chunk，指代题还必须给出上轮可见实体；无答案题要标明应澄清、应拒绝还是可受限外查。人工双标先独立标注，分歧交给仲裁，并把 qrels、corpus generation、评测代码和模型版本一起版本化；开发集只用于选参数，最终 holdout 只在预注册比较时使用。

失败路径同样属于结果：权限过滤后候选为空、证据只找全一半、recipe 不匹配、注入尾巴或模型超时，系统应给 `abstain`、澄清或安全终态，不能强答。评测服务不可把原始简历、录音或企业私密资料混入测试日志；不同 tenant 的 qrels 也不能因为方便调参而相互泄露。对于当前小型本地集，最诚实的动作是扩大为脱敏、真实格式、独立 holdout，而不是反复调 K 直到总分好看。

验证层分别报 Recall@K、nDCG、strict-all、拒答 precision/recall、引用接地、P95 和单 query 成本，并按多证据、指代、ASR、混合语言、代码、域外和安全输入给出分子/分母与区间。发布门要求任何安全/隐私 query 越权证据为 `0`，且任一关键桶回退都可阻断；用真实模型端到端回归加浏览器/状态机测试证明“找到资料”没有在后续被错用。

评测集至少分为 10 桶，每桶建议不少于 20 条：明确单证据、多证据、无答案/域外、指代与省略、错别字与口语、中英混输、代码与日志、题库中不存在的新概念、恶意注入尾巴但前半段是真实问题、用户事实纠正和上下文冲突。

指标至少包括：

```text
Recall@K            有证据问题的覆盖率
nDCG@K              多相关证据的排序质量
Abstain precision   应拒答/澄清时实际拒答的精度
Abstain recall      应拒答/澄清样本被正确拒答的比例
Grounding precision 被下游实际引用的 span 中可验证的比例
P95 latency         query 到可用证据的端到端延迟
```

**发布门**

- 任一安全/隐私 query 的越权证据返回数必须为 `0`。
- 应澄清/拒答集不能只测“返回 5 个 chunk”；必须有明确 `abstain` 标签。
- 模型、embedding、chunk 策略、reranker、语料代际任一变化都重跑同一冻结集。
- 总体分数不得掩盖桶级下降；英文、指代、域外三桶分别设门。

**追问**

- 何时一个 query 有多个“正确 chunk”？
- 如何标注“这个”“上面那题”等需要依赖会话的 query？

**常见错误**

- 只给每条 query 一个“唯一正确 chunk”。
- 用大模型自评替代人工证据标注。
- 把“检索返回了东西”当作“产品回答正确”。

### EXP-C2-02：如何设计 C 端训练数据到 B 端招聘数据的单向、可撤回边界？

**场景**

候选人完成 C 端模拟面试后申请某公司岗位。招聘方希望“直接查看候选人历史模拟面试分数和答案”，候选人只同意提交“本次针对该岗位的候选人面试结果”。设计数据边界、同意模型、撤回流程和越权测试。

**考察点**

- C 端练习数据和 B 端候选评估不是同一资源。
- 用户授权不是 recruiter 的 RLS 权限替代品。
- 逻辑隔离、物理隔离、缓存、checkpoint、trace 的全路径。
- 撤回同意与进行中面试的优先级。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 招聘方可凭候选人 ID 查询 C 端面试。 |
| 4 | 仅靠前端隐藏历史面试。 |
| 7 | 有 `ShareGrant`、范围、期限、撤回和 B 端独立快照。 |
| 10 | 覆盖 DB、向量、缓存、checkpoint、trace、批处理的零越权矩阵。 |

**标准答案**

**90 秒可口述完整答案**

结论是 C 端练习历史与 B 端招聘评估是不同 owner、不同 purpose 的资源；候选人申请岗位并不等于企业可读其全部历史。共享只能通过最小化、岗位绑定、可到期和可撤回的 `ShareGrant`，并在 B 端创建独立 `application_snapshot` 和 `candidate_evaluation`。即使两个资源使用同一个用户 ID，也不能把它们合并成一份可被 recruiter 查询的档案。

流程上候选人先在界面看到将分享的字段、目的、岗位和期限，再由服务端写入 grant 与不可变快照。B 端读请求以 tenant principal 进入，先检查 grant 未过期/未撤回、scope 含当前资源、jobId 匹配，再通过 B 端 owner 边界读取独立评估；C 端 `Interview` 从不以企业 principal 直接查询。缓存、向量、SSE、checkpoint、trace 都使用同一 scope/epoch，命中也要二次授权，不能因为主库 RLS 通过就假定派生路径安全。

撤回是高优先级状态转换：新读取立即拒绝，在途面试停止处理候选人正文，人才库检索、向量、缓存与分享 token 由 outbox 失效。已合法生成且依法需保留的数据放入明确的 retention 边界，不能继续作为可检索画像；清理失败或授权状态未知时 fail-closed。浏览器缓存同样不能视为授权例外，应以短期、加密、scope 绑定内容和刷新后的服务端拒绝收口。

验证采用 A 租户填充、B 租户尝试读取的全路径矩阵，断言 DB、缓存、向量、SSE、checkpoint、trace 各为 `0` 命中；撤回后可检索记录从 `1` 到 `0` 并记录清理 P50/P95/最大值。还要测试同一候选人申请两个租户、grant 过期、撤回与 worker resume 并发、缓存旧副本和 outbox 重放；对外只能说已验证的逻辑隔离能力，不能把 RLS 基线夸大成物理隔离。

- C 端 `Interview(owner_user_id)` 永远不直接授予企业 principal。
- B 端候选人面试独立创建 `candidate_evaluation(owner_tenant_id)`，引用明确提交的、最小化的 `application_snapshot`，不是 C 端训练记录。
- 授权对象独立于 owner-RLS：

```ts
type ShareGrant = {
  id: string;
  subjectUserId: string;
  recipientTenantId: string;
  scope: ('application_resume_snapshot' | 'candidate_evaluation_report')[];
  purpose: 'job_application';
  jobId: string;
  expiresAt: Date;
  revokedAt?: Date;
  consentVersion: string;
};
```

- 撤回后：新读请求立即拒绝；人才库检索和向量索引移除；在途面试转 `terminated_consent`；已合法保存的数据进入独立 retention/法律保留策略；事件账本记录处理结果但不保留不必要原文。

**量化验收**

- A 租户读取 B 租户候选数据：DB、缓存、向量、SSE、checkpoint、trace 各 `0` 命中。
- 撤回后，可检索候选记录数应从 `1` 变为 `0`；后台清理延迟分别记录 P50、P95、最大值。
- “C 端练习数据被 B 端读取”在访问审计中为 `0`。

**追问**

- `ShareGrant` 已过期但报告仍在浏览器缓存中，如何处理？
- 同一个候选人同时申请两个租户，授权如何隔离？

**常见错误**

- “候选人申请过岗位”被误认为同意共享所有历史训练数据。
- 只在主库上做 RLS，漏掉 Redis key、向量索引、LangGraph checkpoint。
- 将“物理隔离”表述为已有事实，但架构实际上仅锁定 RLS 逻辑隔离基线。

### EXP-C2-03：B 端批量匹配怎样避免“带证据的自动淘汰”？

**场景**

某公司上传 10 万份简历，要求系统按 JD 自动排前 200 名。候选人随后说：“简历里的 Kubernetes 经验是自动解析错的，我没有。”招聘方希望保留原排序以方便筛选。设计匹配、事实纠正、公平性和人工决策边界。

**考察点**

- 排名、推荐、自动决策的边界。
- 证据 span、简历快照、事实纠正。
- 受保护属性反事实评测。
- 人工决策记录与不可篡改审计。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 用模型分数直接淘汰候选人。 |
| 4 | 有解释文本，但没有快照和纠正机制。 |
| 7 | 分数绑定证据，纠正后失效并重跑或标注不确定。 |
| 10 | 有反事实配对评测、人工最终决策、统一重算策略和审计版本。 |

**标准答案**

**90 秒可口述完整答案**

我的结论是批量匹配只能做“可解释的辅助排序”，不能由模型分数自动淘汰候选人。排序输入必须是冻结的岗位描述和候选人提交快照；每个贡献维度都能回指到具体证据 span，而不是模型从简历中猜出的技能。最终是否拒绝、推进或录用必须由人创建带岗位相关理由的 `DecisionRecord`，并接受审计和后续 supersede。

流程上，摄取简历后先保存版本和可见范围，再从该快照提取经校验的技能/经历证据，计算辅助分和理由；界面展示的是“该排序受哪些证据影响”和“不确定的维度”，而不是假装客观的命运分数。候选人纠正 Kubernetes 等事实时，相关 span、派生特征和分数立即标 `disputed`；任务队列按统一规则重算同版本人群或将该维度降为不确定，不能为了保留前 200 名而继续把旧断言当决定性依据。

隐私与公平边界包括：受保护属性及其不必要代理变量不进特征；招聘方只看本岗位经授权的应用快照，不看 C 端训练轨迹；模型解释不能泄露他人数据或内部反作弊规则。历史招聘结果若有偏见，不能未经审计直接作为学习排序的真值标签。输入缺证据、纠正待处理、模型异常或公平门失败时，排序降级为人工筛选队列，不能静默自动拒绝。

验证用证据完整率、无证据强结论数、自动淘汰执行数、纠正后残留旧断言数和人工推翻率衡量；反事实配对只翻转受保护属性，报告分差置信区间。还要做同一简历版本重跑一致性、纠正与批处理并发、排序缓存失效和 reviewer 覆盖审计测试。面试官若说“有解释就合法”，我的回答是解释只帮助复核，不能替代授权、反歧视评测和人类最终决策。

- 匹配结果是“辅助排序”，不可直接作为自动拒绝。
- 每个贡献分数来自冻结简历快照中的证据 span；不能引用模型臆造的技能。
- 候选人纠正技能事实后，相关 span 与派生评分标记 `disputed`；系统重跑或将该维度标为不确定，不能继续以旧断言作为决定性理由。
- 最终 `DecisionRecord` 必须由人填写结构化、与岗位相关的理由，绑定证据与评分版本；`finalized` 后只能 supersede，不能覆盖。
- 受保护属性不参与特征；仍需用反事实样本验证代理变量和模型残余偏差。

**量化验收**

- 每一个可见的候选人评分维度有 `>=1` 个证据 span。
- 仅翻转一个受保护属性的配对样本，均值分差 95% CI 落入预设区间；建议 ε 不超过满分的 2%。
- 无证据的强结论数量为 `0`。
- 自动“淘汰”执行数为 `0`；所有拒绝决策均有关联 `DecisionRecord`。

**追问**

- 若历史招聘结果本身带偏见，是否可拿来训练排序模型？
- 如何避免“重新评分”只被用来洗高或洗低特定候选人的分？

**常见错误**

- 把“有模型解释”误当作“决策合法”。
- 用当前简历版本解释历史排序。
- 只测总体组间均值，不做配对反事实样本。

### EXP-C2-04：如何做题库策展、版权治理和错误题召回？

**场景**

运营人员导入 1 GB 中英混排题库，包含网上收集的题目、公司真实训练问题、候选人匿名投稿和带手机号的案例。之后发现一个已发布题目的标准解错误，且已有 1,200 场面试使用过它。设计从导入到下架、重评的全流程。

**考察点**

- 来源、授权、内容指纹、PII、双签、版本快照。
- 候选人可见题面与内部 rubric 的分层。
- kill-switch、缓存/向量清理、在途会话替补。
- 全体一致的重算，禁止选择性洗分。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 题目导入后直接发布。 |
| 4 | 只做文本去重或只做版权声明。 |
| 7 | 有来源状态机、PII gate、双签、版本 pin 和召回。 |
| 10 | 覆盖授权证据、WORM 审计、缓存/向量清理、批量重算幂等和统一策略。 |

**标准答案**

**90 秒可口述完整答案**

结论是题库导入不是把文本塞进向量库，而是一条可暂停、可审核、可召回的内容供应链。最小事实对象包括来源 `QuestionSource`、内容 hash、许可/授权证据、PII 扫描结果、双签记录、`QuestionItem` 版本和发布代际；候选人可见题面与内部 rubric/标准解必须物理或至少权限上分层。任何来源、许可、PII 或审核状态未知时都不能发布。

流程上导入先做病毒/格式校验、去重和来源登记，再进行内容提取、PII 扫描、技术与 HR 独立签核，签核时 pin 内容 hash。hash 一变即回到待审。发布只切换受审核的版本；候选 API 只拿题面和 ID。发现标准解错误或版权投诉时，先把题目转为 `quarantined/recalled`，阻断新发题；在途会话用版本兼容的替补题，已完成会话依据预先定义的统一策略批量重算或不计该题分，而不是挑选某些候选人改分。

失败和隐私处理不能只删主表：扫描服务失败、授权证据缺失、向量/缓存删除未确认、双签人为同一人或 batch 中断，都应阻断发布或保持召回状态。清理由可重放 outbox 驱动，覆盖主库、向量、缓存、题目检索、在途图和导出；审计记录采用不可篡改保留，但不重复存放候选人或侵权原文。版权申诉要能提供来源与处理状态，而不是暴露不必要的原始材料。

验证包括发布前 PII 扫描覆盖率、双签职责分离、召回后新发题数 `0`、所有派生索引残留数 `0`、1,200 场批量重算的幂等与一致性，以及从投诉到缓存失效的端到端追踪。还应抽样测 PII 泛化后题意保真度；若泛化损坏题意或许可无法确认，就不把它作为“可发布题”。

- `QuestionSource` 保存来源 URI、授权/许可类型、内容 hash、审核状态、下架请求和审计记录。
- `QuestionItem` 使用 `imported → enriching → pending_signoff → published → quarantined/recalled/deprecated` 状态机。
- 技术和 HR 双签，不能由同一人完成两种签核；内容 hash 变化后签核失效。
- 发布前 PII 全量扫描；扫描失败时 fail-closed。
- 候选人 API 只发题面和 ID，不发 rubric、标准解、命中证据。
- 标准解错误召回后：新发题数为 `0`；在途会话换替补题；已完成会话统一批量标记；可重算则按统一策略重算，不可重算则“不计该题分”并说明；每个重算任务带 `jobId:candidateId:attempt` 幂等键。

**追问**

- 被投诉版权侵权时，如何验证从召回到缓存失效的完整链路？
- PII 泛化后题意失真，如何量化并阻断发布？

**常见错误**

- 认为“改一行标准解”即可。
- 用题库标准解原文作为候选人解释内容。
- 只删除主库记录，缓存和向量召回仍能命中旧题。

### EXP-C2-05：如何设计可恢复 Agent 图，处理非作答、指代、跳过和断线恢复？

**场景**

用户在同一题中依次发送：“这个我不会。”“那上面那个为什么要这么做？”断网并在 3 天后恢复，恢复后点击两次“继续”。设计图拓扑、持久状态、事件和副作用边界。

**考察点**

- `interrupt` 重放语义。
- `clarify`、`unresolved`、`ingest` 的确定性路由。
- `threadId`、checkpoint、事件账本和租约。
- 节点副作用、模型调用幂等和终止预算。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 在内存中保存 `sessionId → Promise resolver`。 |
| 4 | 有 checkpoint，但出题和等待用户放在同一有副作用节点。 |
| 7 | 题目持久化、等待用户、评分、收尾分离；恢复不会重复出题。 |
| 10 | 有确定性 route 事件、租约竞争处理、turn 幂等键、最大澄清次数与恢复测试。 |

**标准答案**

**90 秒可口述完整答案**

结论是可恢复图的核心不是保留一个浏览器连接，而是把业务事实、运行状态和副作用边界分开。题目、答题 turn、评分、消费和完成报告是数据库/事件账本的事实；LangGraph checkpoint 只保存能恢复控制流的最小状态。等待用户的节点必须是纯 `interrupt`，这样断线三天、重复点击“继续”或 worker 重启都不会重新出题、重复扣费或因模型随机性换分支。

具体流程是先生成并持久化题目，再进入 `awaitAnswer`；收到输入后把确定性分类结果写为 `route_decided`，再分别进入评分、未解决、危机安全暂停或下一题。明确“不会”可允许一次澄清，第二次非作答或跳过进入 `unresolved`；“上面那个”只有在当前可见实体唯一时解析，否则澄清。每个 turn、模型调用和写副作用都有稳定 ID；resume 先竞争 thread lease/CAS，失败者只读取已经推进的状态。

异常时，checkpoint 不可读、route schema 不合法、租约过期、预算耗尽或危机输入都不能让图重新从 START 盲跑。它们分别进入人工恢复、受限澄清、回查既有命令、停止外呼或安全升级终态。候选人的原始答案和高敏文本不能被无限 append 到 checkpoint/trace；仅保留有 retention 的 artifact ref 和必要审计字段，撤回同意后也要阻断 resume。

验收通过 crash-at-every-edge、同一 resume 20 路并发、事件乱序/重复、三天后恢复、最大澄清次数、模型超时和危机场景矩阵完成。硬不变量是每题 `clarification_needed <= 1`、推进成功数 `1`、同一 turn 的评分/消费各为 `1`、事件序号无缺失重复；同时观察恢复 P95、人工恢复率和因不确定性进入降级的比例。

```text
START
  → genQuestion
  → persistQuestion
  → awaitAnswer(interrupt only)
  → classifyTurn
  → evaluateAnswer / markUnresolved / safetyHold
  → nextQuestion / finalize / degrade
```

- `awaitAnswer` 节点在 `interrupt()` 之前不得产生副作用。
- “不会”可以澄清一次；第二次非作答或明确跳过转 `unresolved`，换题或结束，不无限追问。
- 语义路由结果持久化成 `route_decided`，恢复时读取原决定，不能因模型随机性进入不同分支。
- 双击 resume 通过 thread lease/CAS 仅允许一个执行者推进；失败者回查当前状态。
- 业务事实在数据库和事件账本中，checkpoint 仅承载运行态。

**量化验收**

- 任意题目 `clarification_needed <= 1`。
- 同一 resume 并发 20 路：推进成功数 `1`。
- 进程重启后事件序号无重复、无缺失、连续。
- 同一 turn 的模型收费记录、评分事件和消费确认分别为 `1`。

**追问**

- 为什么把模型出题放在包含 `interrupt()` 的节点前面？
- “危机自伤”输入与“我不会”的状态转换为什么不同？

**常见错误**

- 把“用户没回答”当成低质量回答，导致能力分下降。
- 把等待用户连接存在内存或 SSE 连接中。
- 在可重放节点中直接扣费或调用外部模型。

### EXP-C2-06：Prompt 或模型变更怎样做实验，而不污染评分与招聘决定？

**场景**

团队要把评分模型从 A 切换到 B，并把新 prompt 灰度给 10% 用户。B 端招聘方要求“先给低分候选人用新模型看看效果”。设计实验单元、冻结策略、观察指标、停止条件和回滚。

**考察点**

- 训练产品实验与招聘决策实验的风险差异。
- 随机化、版本 pin、同一会话一致性。
- 质量、安全、公平、成本和延迟共同门控。
- 影子评测不能改变生产业务事实。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 按候选人分数定向分流模型。 |
| 4 | 只比较平均分或主观满意度。 |
| 7 | 有稳定分桶、版本 pin、影子模式和回滚。 |
| 10 | 明确禁止按受保护属性/历史分数定向，定义统计功效、停止条件和不可突破的安全门。 |

**标准答案**

**90 秒可口述完整答案**

结论是 C 端训练产品可以在明确同意下做受控实验，但 B 端招聘结果不能拿候选人的历史低分、受保护属性或脆弱群体作定向试验对象。模型/Prompt 变化首先是质量与公平风险，而不是转化率按钮；在招聘域，新版本先离线和影子运行，不能单独改变候选人可见分数、报告或招聘决定。

实验对象以稳定 hash 分桶，同一 interview 在开始时 pin `promptVersion`、`modelVersion`、rubric 和题目版本，保证一场面试不会中途换尺子。影子分支只消费脱敏、最小化输入并写入独立评测表；它可产生对照分、证据和成本，但不能写主评分、权益、C/B 报告或 `DecisionRecord`。若需 C 端 canary，则要明确同意、随机化单位、最小样本、观察窗和可回滚版本；C/B 数据仍不得因为使用同一模型而互相复用。

当样本量不足、模型输出 schema 失败、证据不足、安全门或公平门触发、成本/P95 超预算时，实验停止放量并回到已 pin 的稳定版本。不能在同一场里把“低分候选人”放到实验组后再用实验结果证明它更适合低分人群，这既有选择偏差，也可能构成不公平招聘处理。影子数据保留期限、访问角色和删除传播也需独立于生产招聘档案。

验证不只比较平均分：报告每桶证据可验证率、纠正后错误前提率、安全泄露、正常答案误拒、反事实公平、P50/P95、单场成本、申诉与人工推翻率，并预先定义统计功效、停止阈值和安全硬门。若任一不可突破门失败，哪怕平均成本下降也不发布；回滚要能把新请求切回旧版本，并确保正在进行的会话仍按已 pin 版本完成。

- C 端训练可做经同意的实验；B 端涉及招聘时，优先影子运行和离线评测，不能用新模型单独改变候选人结果。
- 分桶键稳定，例如 `hash(principalId + experimentId)`；同一 interview 必须 pin `promptVersion` 和 `modelVersion`。
- 影子输出仅写脱敏评测表，不写评分、报告、招聘决策或候选人可见事件。
- 实验指标至少包括：证据可验证率、事实纠正后的错误前提率、安全泄露率、正常答案误拒率、反事实公平指标、P50/P95 延迟、单场成本、申诉率、人工推翻率。

**追问**

- 为什么不能按“低分候选人”定向实验？
- A/B 的样本量和显著性不足时能否提前宣布 B 更优？

**常见错误**

- 用“模型分高了”作为质量提升证据。
- 改模型后让同一场面试不同轮次的评分标尺漂移。
- 先上线再补评测集。

## 高级（5 题）

### EXP-C3-01：模型调用为什么不能轻易声称 exactly-once？怎样做成可对账的至多一次结果？

**场景**

服务端向模型供应商提交评分请求后，在收到响应、写数据库之前崩溃。worker 重启后重新执行该 turn。供应商是否已经计算并收费未知。设计调用账本、供应商幂等、重试、对账和降级。

**考察点**

- 外部副作用与数据库事务边界。
- `in_flight`、`committed`、`failed`、不确定状态。
- provider idempotency key、请求指纹和人工对账。
- 不在网络调用期间持数据库锁。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 声称数据库唯一索引可保证模型外呼 exactly-once。 |
| 4 | 本地缓存模型结果，但不处理崩溃窗口。 |
| 7 | 有调用账本和 provider idempotency key。 |
| 10 | 说明无法单方数学保证，定义不确定态、对账、预算上限和用户可见降级。 |

**标准答案**

**90 秒可口述完整答案**

结论是本地数据库最多能保证本地账本与结果的原子性，不能单方面证明模型供应商恰好计算和收费一次。跨网络调用存在“供应商已执行、我方在落库前崩溃”的不确定窗口，因此目标应表述为：相同业务命令向用户至多提交一份已验证结果，外部调用尽可能使用供应商幂等键并且所有不确定状态可对账、可降级、可审计。

流程从一个确定性 `idempotencyKey` 和 `requestHash` 开始。服务端先短事务写 `reserved/in_flight` 调用账本和预算预留，再在事务外将同一键传给支持幂等的 provider，记录 `providerRequestId`；响应只是一份候选数据，必须经 schema、引用/业务规则和消费核算校验，才以短事务把 `committed + result + usage` 一起落库。重复请求先查账本，已 committed 直接返回原字节级结果，绝不重新评分。

崩溃、网络断开、provider 超时或账本 lease 到期时，不无限重试。能按供应商 key 查询就先对账；明确未执行才在预算内重试；无法确认就进入 `unknown`/人工对账或用户可见的延迟完成状态，并单列未知成本。调用网络期间不持数据库行锁或 advisory lock，以免把供应商慢请求放大成连接池和事务雪崩。供应商没有幂等接口时，只能缩小重复概率和做好对账，不能承诺收费 exactly-once。

验证包含在发送前、发送后、收到响应后、提交前逐点注入崩溃，检查同 key 的已提交结果字节一致、`in_flight` 都有终态、重试受预算限制。线上监控悬挂记录数量/最长年龄、provider 查询成功率、未知费用、fallback 深度、重复提交和人工对账时长；这些指标决定是否暂停该供应商或降级，而不是用一次正常调用证明可靠。

1. 先写调用账本 `reserved/in_flight`，其中有确定性 `idempotencyKey` 和 `requestHash`。
2. 向支持幂等的供应商传递同一 key；供应商返回 `providerRequestId`。
3. 结果经过 schema 与业务校验后，原子提交 `committed + result + usage`。
4. 崩溃后：已 committed 返回原字节级结果；in-flight 且可按 provider key 查询则对账；无法确认时不得盲目无限重试，进入受限重试或降级，并记录未知成本。
5. 模型调用不得持有长事务、行锁或 advisory lock。

**量化验收**

- 相同 key 的已提交结果字节一致率 `100%`。
- `in_flight` 超时记录有对账终态，悬挂数量与最长年龄必须监控。
- 重试总次数、fallback 深度、模型费用不确定记录都可审计。

**追问**

- 供应商没有幂等接口时，系统对“收费次数”和“用户结果”分别能承诺什么？
- 为什么“在一个数据库事务里调用模型”反而扩大故障面？

**常见错误**

- 把本地 `UNIQUE` 当作外部调用的 exactly-once。
- 对 `in_flight` 记录无限重试。
- 将模型输出未经业务校验直接记为 committed。

### EXP-C3-02：当系统宣称 C/B “物理隔离”，但现实是 RLS 逻辑隔离时，架构师如何做决策？

**场景**

产品要求“C 端训练数据与 B 端招聘数据物理隔离、永不互通”。当前数据库方案是同库、不同 owner 列、RLS 和 `principal` 上下文。B 端还会使用缓存、pgvector、LangGraph checkpoint 和 tracing。给出目标架构选择、威胁模型、迁移路径和验收。

**考察点**

- “物理隔离”和“RLS 逻辑隔离”术语不能混用。
- 数据平面与控制平面分离。
- 连接池 GUC 泄漏、BYPASSRLS、后台 worker、缓存、向量和 trace。
- 成本、运维、爆炸半径与迁移顺序。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 认为 `WHERE tenant_id = ?` 等于物理隔离。 |
| 4 | 只提 RLS，不覆盖非主库路径。 |
| 7 | 明确 RLS 是逻辑基线，并给出全路径测试。 |
| 10 | 给出 schema-per-tenant / 独立库的 ADR 维度、迁移策略和可验证的隔离 SLO。 |

**标准答案**

**90 秒可口述完整答案**

结论是同库 RLS 是重要的逻辑隔离基线，但不能被称为物理隔离。它依赖正确的 principal 绑定、数据库角色、查询路径和连接池行为；任何 `BYPASSRLS`、漏设上下文或旁路缓存都可能扩大越权面。是否升级为 schema-per-tenant、独立数据库或独立 C/B 数据平面，应写成 ADR，按监管、客户隔离要求、数据敏感度、爆炸半径、恢复目标、成本和运维能力选择，而不是用一个营销词替代决策。

当前流程应让每个请求和后台 job 都携带最小 principal，在事务内参数化设置上下文，由数据库 RLS 决定行可见性；`owner_user_id XOR owner_tenant_id` 等约束防止资源同时混属。主库只是其中一路：Redis key、向量检索过滤、LangGraph checkpoint、SSE 重放、trace 和批处理导出都须从同一授权对象派生 namespace/过滤。高权 dispatcher 只调度，不读取候选正文；连接池采用不会把前一主体 GUC 遗留给下一主体的事务模式。

迁移时不能停服后直接切库。先定义旧/新数据平面的写双投和版本/幂等约束，做影子读校验与越权探针，再冻结旧写、可恢复地回填并逐步切读；任一主体、缓存或 worker 路径的授权不确定时 fail-closed。审计既记录拒绝也记录高权角色、RLS 上下文和跨平面访问，避免只在 API 层看起来干净。

验收以无 principal 查询 `0` 行、主库/向量/缓存/checkpoint/SSE/trace 跨租命中均为 `0`、连接池连续复用无串号、所有 B 端 job 有 tenant principal 为硬门。用并发连接池、过期 cache、vector post-filter、管理员角色误配和迁移回滚做故障注入；达到这些只能证明逻辑隔离合同，若对外承诺物理隔离还需相应独立基础设施和恢复演练证据。

- 同库 RLS 是逻辑隔离，不应对外称为物理隔离。
- 最低要求：`owner_user_id XOR owner_tenant_id` 约束；事务内参数化 `set_config`；应用角色无 `BYPASSRLS`；事务模式连接池；worker job、Redis key、向量、checkpoint、trace 具有 principal 边界。
- 对高敏招聘数据，在 ADR 中比较 shared DB + RLS、schema-per-tenant、database-per-tenant、独立 B/C 数据平面；比较隔离强度、合规、运维、成本、恢复目标和爆炸半径。
- 迁移先做写双投、读校验、冻结旧路径、回填、越权探针，不能直接切库。

**验收**

- 无 principal 查询：`0` 行。
- 跨租读取：主库、向量、缓存、checkpoint、SSE、trace 均为 `0`。
- 连接池连续复用的跨主体探针 `0` 次串号。
- 每个 B 端批处理任务均有租户 principal；高权 dispatcher 不读取候选正文。

**追问**

- 何种客户或法规情形会把 RLS 基线升级为独立数据库？
- 如何设计 audit，发现某个高权角色意外拿到 `BYPASSRLS`？

**常见错误**

- 把 app 层 `WHERE` 条件当作隔离机制。
- 忽略 PgBouncer/session 复用导致的 GUC 串号。
- 只做 API 越权测试，未覆盖缓存和可观测性后台。

### EXP-C3-03：如何设计招聘系统的撤回同意、注销和并发优先级？

**场景**

同一时刻发生：候选人撤回面试同意；worker 正在 resume 面试；企业正在 offboarding；HR 正在导出候选人报告；支付和权益对账任务正在运行。定义优先级、状态机、事务边界和最终可观测结果。

**考察点**

- 撤回同意优先于继续处理个人数据。
- 不同聚合之间通过 saga/outbox 协调。
- in-flight 阻断、幂等与补偿。
- 合法保留与可检索数据删除的区分。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 仅删除用户记录。 |
| 4 | 有撤回按钮，但不处理运行中的 worker。 |
| 7 | 明确 `terminated_consent`、导出阻断、人才库移除和事件日志。 |
| 10 | 给出并发裁决顺序、CAS 守卫、可重放补偿和不变量压测。 |

**标准答案**

**90 秒可口述完整答案**

结论是撤回同意不是一个“隐藏页面”的 UI 事件，而是高优先级、可线性化的业务命令；它必须胜过 resume、导出和新的模型处理。系统要区分候选人内容、可检索画像、运行中 job、企业席位和财务凭证：前四类应停止新处理并按政策清理，财务凭证若依法需要保留则去标识化、最小权限保留，不能继续用于检索或招聘决策。

流程上 `withdraw_consent` 以稳定 command ID 和 CAS 从可处理状态切到 `terminated_consent`，同时写事件/outbox。每个 worker 在读取正文、调用模型、提交评分、导出前重新检查最新 consent version；HR 导出也只能读取撤回前已合法生成且政策允许的快照，否则阻断。outbox 分别驱动 ShareGrant、人才库、向量、缓存、checkpoint、排队 job 和浏览器会话失效，完成情况带可重放的清理状态和残留计数。

并发中不能依赖“谁先到谁赢”的偶然顺序。resume 与 withdraw 冲突时以 withdraw 为终态，lease 持有者在下一个副作用边再次 CAS；企业 offboarding 先禁止新写和新导出，已有清理/支付对账按各自合法保留规则继续，但不得读取候选人正文。已经发送给供应商的模型请求无法收回已离开系统的数据，这个边界要如实告知；系统能保证的是不再发新请求、最小化供应商合同、记录处理状态并阻断结果回写为招聘依据。

验证要混压 withdraw、resume、offboarding、导出和对账，断言最终面试必为 `terminated_consent`、无越权导出、无双扣费、无 0-owner、`seatUsed <= seatQuota`，且清理重放不会重复产生副作用。监控撤回到各派生系统不可检索的 P50/P95/最大值、未完成清理队列和撤回后尝试读取数；任何大于 `0` 的新处理尝试都是需要阻断的安全事件。

- `withdraw_consent` 必须可线性化为一个有序事件；resume 前重新读取最终 consent 状态。
- `withdraw` 胜过 `resume`：面试转 `terminated_consent`，不得再调用模型处理候选人文本。
- 企业 offboarding 后禁止新写；导出仅允许明确的已生成快照或直接阻断，取决于保留政策。
- 人才库、向量、缓存、分享授权、进行中 job 通过 outbox 驱动清理。
- 支付凭证与个人内容的保留期限、去标识化与访问权限必须分开设计。

**必要并发测试**

- `withdraw` 与 `resume` 并发：最终态必为 `terminated_consent`。
- 4 类操作混压后：无双扣费、无 0-owner、`seatUsed <= seatQuota`、无越权导出。
- 清理任务重放：重复删除副作用为 `0`。

**追问**

- 一个在途模型调用已经发送给供应商时，撤回同意可以保证什么，不能保证什么？
- 候选人撤回后，财务凭证如何合法保留而不再可检索？

**常见错误**

- 将撤回同意仅实现为 UI 隐藏。
- 允许已排队的 worker 在撤回后继续读取正文。
- 将整个跨聚合清理放进一个长事务。

### EXP-C3-04：如何定义 Agent 的真实模型发布门，而不是只跑 happy-path golden case？

**场景**

团队的已有集主要是正常简历、正常 JD、正常答案，测试均通过。请设计一次模型、prompt、图拓扑或安全规则变更的发布门。

**考察点**

- 真实模型、fake model、确定性逻辑测试的职责分工。
- 安全与正常回答的双侧指标。
- 分层样本、最小样本、版本冻结、回归分析。
- 失败后的阻断、灰度与回滚。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 只增加几个 prompt 注入样本。 |
| 4 | 有红队集，但没有正常反例和阻断动作。 |
| 7 | 定义多桶数据、真实模型运行、指标和阈值。 |
| 10 | 同时覆盖安全、接地、事实纠正、误拒、成本、延迟、公平、状态机和端到端浏览器测试。 |

**标准答案**

**90 秒可口述完整答案**

结论是发布门要把“确定性系统合同”和“真实模型统计质量”分层；fake model 可以证明状态机、RLS、CAS 和幂等管道，但不能证明真实模型会在攻击、指代、长文本或正常高级回答上表现正确。任何模型、prompt、图拓扑或安全策略变更，都必须带冻结数据/版本、预注册比较对象、明确的阻断条件和可回滚版本，而不是只新增几个攻击样本后看总体通过率。

第一层运行确定性测试：授权、事件序号、账本、状态转换和副作用在故障重试下仍满足不变量。第二层用真实模型跑分桶离线集，输入必须同时有攻击与正常高质量技术回答，并标注所需证据、期望澄清/拒答、纠正事实和成本预算；检索、生成、引用与路由分别计分。第三层启动真实浏览器端到端流，覆盖作答、双击、断网、SSE 重放、额度、撤回同意、B 端越权和长文本渲染，验证模型输出没有在 UI 或业务状态机中被错误放大。

失败语义写在门里而不是上线后临时判断：安全/越权/重复扣费任一硬门失败立即阻断；模型质量或成本/P95 回退先 shadow、限量 canary 或回滚到已 pin 版本；样本不足、标注争议、provider 故障则不把“无结果”算作成功。所有评测输入需脱敏、目的受限和有 retention，攻击样本也不能含真实候选人秘密。

验证报告必须给每桶分子/分母、区间、版本和失败样本，而不是一条平均分。硬门可包括秘密泄露、跨 principal 访问、显式纠正后重复错误前提、重复扣费均为 `0`，以及所有事实性评分维度有证据；软门包含正常答案误拒、接地、P95、成本、公平和人工推翻率。若成本下降但事实纠正错误前提上升，按预设质量门不发布；监控触发后自动停止放量并回滚。

发布门应有三层。

1. **确定性层**：RLS、幂等、CAS、事件序号、状态机、校验器；fake model 仅验证管道，不宣称模型质量。
2. **真实模型离线评测层**：覆盖指代、省略、乱码、错别字、跑题、注入、索取隐私、刷分、事实纠正、危机、长文本、混合语言、正常高级答案；每桶单独报告。
3. **真实浏览器端到端层**：启动、作答、双击、断网、恢复、SSE 重放、额度、报告、撤回同意、B 端越权、长文本渲染；记录请求到终态 P50/P95、事件数、重复副作用数、DOM 节点数或前端长文本性能指标。

**建议硬门**

```text
agent_output_secret_leak = 0
cross_principal_access = 0
same_false_premise_after_explicit_correction = 0
duplicate_charge = 0
normal_answer_false_rejection <= 预先设定阈值
all fact-bearing score dimensions have evidence = 100%
```

**追问**

- 为什么攻击集拦截率很高时，仍要关注正常高级技术答案的误拒？
- 若模型输出成本降低 20%，但事实纠正后的错误前提率上升，是否可发布？

**常见错误**

- 用 fake model 测出“安全”后宣布真实模型安全。
- 只测攻击拦截率，不测正常技术答案误杀率。
- 没有将未通过的质量门绑定到阻断发布或自动回滚。

### EXP-C3-05：设计一个“面试训练 + 企业招聘”端到端系统，并说明哪些能力绝不能共享

**场景**

请在 45 分钟内设计 Meetwise 的目标系统。它包括 C 端简历、模拟面试、报告、成长计划和支付；B 端岗位、候选人投递、候选人 AI 面试、人才库和人工决策；同一套模型运行时与题库能力；真实用户会乱问、纠正简历、双击、断网、撤回同意；生产目标要求可恢复、可审计、可量化评测。

**考察点**

- 领域边界，而不是画一张技术组件图。
- 哪些引擎可以共享，哪些数据、状态、权限、评分不能共享。
- Agent、RAG、支付、同意、招聘决策的组合风险。
- 发布、回滚、观测、人工接管。

**10 分评分锚点**

| 分数 | 可观察条件 |
|---:|---|
| 0 | 只画前端、后端、LLM、向量库。 |
| 4 | 说有微服务和多 Agent，但未定义事实源和状态机。 |
| 7 | 识别 C/B 边界、业务表/运行态分离、四个生产原语。 |
| 10 | 同时给出数据流、状态机、授权、模型调用账本、评测门、SLO、失败与回滚。 |

**标准答案**

**90 秒可口述完整答案**

我的总体结论是共享“受限的技术能力”，不共享“用户拥有的事实与决策权”。C 端的 Resume、Interview、AssessmentReport 和 Entitlement 以用户为 owner；B 端的 Job、ApplicationSnapshot、CandidateEvaluation 和 DecisionRecord 以租户为 owner。两侧可以共用 AI runtime、题库策展、模型调用账本、观测与发布工具，但 C 端练习原文、历史训练评分、成长档案和 C 端授权上下文绝不能因为账户相同或模型相同而被 B 端读取。

数据流从明确的产品动作开始：C 端训练只读用户自己的简历/题库快照并生成可申诉报告；候选人申请 B 端岗位时，通过目的限定、最小化、可撤回的 grant 创建独立 application snapshot，B 端 Agent 只在该 snapshot 和岗位权限内运行。业务表保存事实和状态机，`AiGraphRun/checkpoint` 只保存运行控制态与 artifact ref；所有写操作以 principal RLS、CAS、幂等键、事件账本和必要的 outbox 约束。模型输出经过 schema、证据和业务校验后才可能影响评分，支付、退款和最终招聘决定不由 Agent 文本直接执行。

系统发生模型超时、重复点击、断线、事实纠正、授权撤回、题库召回或 provider 不确定收费时，各自有明确终态：读取已有命令、澄清/未评分、安全暂停、`terminated_consent`、替补题/统一重算、对账或降级。高敏数据跨边界、授权不确定、generation/版本不匹配或缓存 scope 异常时 fail-closed；招聘排序只做辅助，最终人为 `DecisionRecord` 绑定证据和版本。不能承诺“100% 高可用”，只能把可证明的不变量和可演练的恢复目标分开。

验证覆盖 C/B 全路径越权为 `0`、同 command 已提交副作用为 `1`、题库召回后新发题为 `0`、撤回后可检索残留为 `0`，并独立报告真实模型评测、浏览器 E2E、P95/成本、公平、申诉与人工推翻。发布走离线门、shadow、canary、观察窗和版本回滚；可靠性目标写成 RTO、RPO、SLO、降级语义和演练频率，不能把一轮本地测试包装成生产承诺。

```text
C 端：
User-owned Resume / Interview / AssessmentReport / Entitlement

B 端：
Tenant-owned Job / ApplicationSnapshot / CandidateEvaluation / DecisionRecord

共享：
AI runtime、题库策展能力、模型调用基础设施、审计规范

不可共享：
C 端练习原文、历史训练评分、成长档案、C 端授权上下文
```

必须出现的设计结论：

- `Interview` 业务事实与 `AiGraphRun/checkpoint` 运行态分离。
- 所有状态改动均以 CAS、幂等键、principal RLS、持久有序事件日志约束。
- C 端用户数据进入 B 端只能通过最小化、目的限定、可撤回的授权与独立快照。
- 招聘排序可辅助，不可替代人工最终决定；最终理由绑定证据、版本和审计。
- 题库必须可下架、可召回、可统一重算。
- 模型输出需经过 schema 与业务双校验；模型并不是真实事实源。
- 每次模型变更由真实模型对抗评测、正常反例和浏览器 E2E 共同门控。

**追问**

- 哪些接口必须使用同步事务，哪些应通过 outbox/后台 job？
- “100% 高可用”在本系统中应如何拆成 RTO、RPO、SLO、降级语义和演练频率？

**常见错误**

- “同一个用户 ID”就视为可以共享数据。
- 让 Agent 直接扣费、退款、更新招聘决策。
- 把 checkpoint 当作唯一业务真相。
- 声称“100% 高可用”但未定义 RTO、RPO、单点和降级语义。
